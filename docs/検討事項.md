# 検討事項

チームで決めるべき設計・方針のメモ。

---

## 1. 認証の方式 → フロントからCognito SDK直接

フロントが Amplify Auth（Cognito SDK）を直接叩く構成に決定。

```
フロント → Cognito SDK（直接）
```

- バックエンドに認証コードを書かなくてよい（工数削減）
- トークン管理も SDK が自動でやってくれる
- API Gateway の Cognito Authorizer で JWT を検証し、バックエンドはビジネスロジックに集中
- openapi.yml の `/auth/*` エンドポイント5つは不要になる

---

## 2. 店舗データの登録 → ユーザー投稿型（Storesテーブル廃止）

ユーザーが自由にトイレ情報を投稿できる形に決定。

- Stores テーブルを廃止し、Toilets テーブルにコンビニ名・ブランド・住所・位置情報を統合
- 「店舗を選ぶ → トイレを登録」の2ステップではなく、1回の投稿で完結
- `GET /stores` エンドポイントも不要

---

## 3. MVP のスコープ → 高優先度のみ

ハッカソン期間内に完成させるため、高優先度の機能のみ実装。

| 機能 | 優先度 | 対応 |
|------|--------|------|
| トイレ情報の登録・取得 | 高 | ✅ MVP |
| マップ上での表示 | 高 | ✅ MVP |
| 画像アップロード（S3） | 高 | ✅ MVP |
| 画像審査（Rekognition） | 中 | 後回し |
| 虚偽報告・自動削除 | 中 | 後回し |
| ナビゲーション + AI提案（Bedrock） | 低 | 後回し |
| プッシュ通知（位置情報監視） | 低 | 後回し |

---

## 4. ページネーション → 後回し

- 地理検索（位置 + 半径）で取得するのでデータ量は限定的
- ハッカソンデモ規模では不要
- MVP後にAPIを変えてもユーザーは自分たちだけなので breaking change の問題なし

---

## 5. Docker → DynamoDB Local を docker-compose で使用

- 各メンバーがローカルで独立してDBを触れる
- テーブル作成スクリプトを用意し `docker compose up` 一発で環境構築
- AWS認証情報の共有が不要
