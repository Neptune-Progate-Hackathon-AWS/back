# 検討事項

チームで決めるべき設計・方針のメモ。

---

## 1. 認証の方式

### 現状の設計
openapi.yml に `/auth/signup`, `/auth/login` など5つのエンドポイントが定義されている。
バックエンド（Lambda）が Cognito を呼び出す構成。

```
フロント → API Gateway → Lambda → Cognito
```

### 検討ポイント
フロントが Amplify Hosting なら、Cognito SDK（Amplify Auth）をフロントから直接叩く方が一般的。

```
フロント → Cognito SDK（直接）
```

**メリット:**
- バックエンドに認証コードを書かなくていい（工数削減）
- Cognito の機能（MFA、ソーシャルログイン等）がそのまま使える
- トークン管理も SDK が自動でやってくれる

**デメリット:**
- フロント側に Cognito の設定が必要

**→ どちらにするかチームで決める**

## 3. MVP のスコープ

### 現状の設計
openapi.yml に定義されている機能が多い。全部作るとハッカソン期間内に終わらない可能性がある。

### 機能一覧と優先度（案）

| 機能 | 優先度 | 備考 |
|------|--------|------|
| トイレ情報の登録・取得 | 高 | コア機能 |
| マップ上での表示 | 高 | コア機能 |
| 画像アップロード（S3） | 高 | トイレ登録に必要 |
| 画像審査（Rekognition） | 中 | なくても動く。後からでもOK |
| 虚偽報告・自動削除 | 中 | MVP 後でもいい |
| ナビゲーション + AI提案（Bedrock） | 低 | デモ映えするが工数大 |
| プッシュ通知（位置情報監視） | 低 | 工数に対してインパクト小 |

**→ まず何を作って、何を後回しにするか決める**

## 4. ページネーション

### 現状の設計
`GET /toilets`, `GET /stores` にページング（limit/offset や cursor）がない。

### 検討ポイント
- ハッカソンのデモ規模なら不要かもしれない
- 後から足すと API の breaking change になる

**→ 今入れるか、後回しにするか決める**

---

## 5. Docker の利用

### 検討ポイント
- Go はバイナリ1つで動くので、ローカル開発では基本不要
- DynamoDB Local を使うなら docker-compose で立てると便利
- SAM CLI（Lambda ローカルテスト）は内部で Docker を使う

**→ DynamoDB Local を使うかどうかで判断**
